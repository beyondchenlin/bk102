# 桌面连续预览冷启动定位与修复

2026-11-08，最终插件 `0.2.0-desktop.11`。仅修改桌面插件的浏览器播放准备流程，沿用官方 DSH `0.2.1-rc.2` 的隔离演示。首页、裁切算法、工程服务和 FFmpeg 预览／导出管线未改；未接入 Android、Media3 或修改 DSHA 宿主。

## 结论与对照依据

本轮复现的是**新生成代理首次定位后，播放时钟先于首帧显示准备完成而启动**的问题。旧客户端在 `loadedmetadata` 中设置 `currentTime` 后立即调用 `play()`，此时仍为 `readyState=1`、`seeking=true`。现有代理反复播放六次没有掉帧；新代理从 4 秒样本的 1.8 秒处起播，旧实现两次分别报告 17 和 8 帧丢帧，覆盖了 2 秒的镜头接缝。同期未记录到主线程长任务。

在同一浏览器、同一工程和同一编码管线下，仅替换页面启动顺序的两次对照均为 0 丢帧。旧流程与最终修复生成的 4 秒预览文件 **SHA-256 完全相同**，独立解码也没有缺帧。因此这次问题归于客户端启动与浏览器解码／合成准备的配合，不是镜头拼接漏帧或导出少帧。浏览器媒体诊断观察到 `D3D11VideoDecoder`；没有据此认定某个显卡驱动存在普遍缺陷，也没有关闭硬件解码掩盖问题。

依据：[loadedmetadata 事件](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/loadedmetadata_event)表示元数据可用；[requestVideoFrameCallback](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)可观察视频帧提交给合成器。[丢帧计数](https://developer.mozilla.org/en-US/docs/Web/API/VideoPlaybackQuality/droppedVideoFrames)与媒体文件的解码帧数是不同指标，本报告分开记录。

## 最终实现

新增 `plugins/dsh-copy-edit/src/preview.cjs`，由既有构建内联，不新增依赖、网络端口或宿主权限：

1. 保持暂停，等待元数据，定位到目标时间。
2. 等待定位完成和可播放数据，再确认固定 30fps 代理的目标帧已提交；前一帧不算就绪。
3. 跨两个浏览器绘制机会后启动播放。这里等待实际事件，没有加入固定秒数的假进度。
4. 准备期间可取消。新定位、离开工程、重新裁切或卸载会撤销旧请求、帧回调和监听，迟到事件不能重新播放。各准备阶段有 10 秒截止，失败明确显示错误。
5. 续播读取播放器实际时间，避免回到低频更新的页面读数。播放状态以实际 `playing` 事件为准。

严格首帧检查还发现一个边界错误：时间轴传入 `59/30`，浏览器实际 `currentTime` 可截断为 `1.966666`，落到前一帧。最终版只在定位时向目标帧内部做微秒级偏移，工程帧号、逻辑位置及编码时间戳不变，补了专门回归。没有将帧匹配条件放宽来跳过错误。

播放指针的现有 `timeupdate` 更新方式未重构，本轮没有把时间轴动画升级当作视频掉帧修复。没有 `requestVideoFrameCallback` 的浏览器走定位／缓冲加绘制机会的兼容路径；该兼容路径不在本机流畅度验收范围内。

## 失败与修正记录

- `Browser.getVersion` 在当前 Ego 协议不支持，改用页面 UA 与支持的 Media 诊断；未另开浏览器绕过。
- 第一次取消准备的自动化等待错过了短暂状态，后续预先监听状态并触发实际按钮处理器，取消及迟到事件保护通过。
- 第一次续播断言拿异步 `play` 事件时间当作调用起点，受到音频时钟推进影响；改为同时记录 `play()` 调用和事件，确认调用时间不回跳，保留两组记录。
- desktop.10 严格首帧条件暴露了微秒截断问题，记录 `exact-seek-failure.json`；desktop.11 修复后实际时间轴定位和续播通过。
- 60 秒夹具在追加最后一个未裁切素材时触发既有总长限制。复用同一个测试工程，临时缩短本任务镜头，追加并裁切后恢复，未修改上限或新建多套环境。
- 安装器仍有宿主 peer dependency 提示，实际宿主加载成功；不称日志零警告或全程一次通过。
