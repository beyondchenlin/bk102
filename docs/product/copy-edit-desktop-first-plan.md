# 桌面优先与移动适配边界

日期：2026-11-08。调整依据：用户希望先完整验证桌面业务，并要求不要把“响应式网页”误认为移动端媒体能力已经实现。

## 判断

**采用桌面优先的业务开发顺序，但不能采用“桌面全部做好，最后只缩放到手机”的工程假设。**

产品仍然是同一个遵循 DSH 规范的文案剪辑插件。业务、工程格式和大部分前端共用；移动端界面按触摸和窄屏重新组织；桌面和 Android 各自实现媒体执行适配器。Android 部分原生开发不可省略，但无需把文案库和整个编辑界面重写为原生 App。

| 层 | 复用与适配判断 |
| --- | --- |
| 文案、分类、搜索、V1/V2、工程与素材引用 | 共享业务模型和 DSH Host 服务；仍需持久化、冲突和重开验证 |
| API 对话、公司素材/TTS 接口 | 共享协议与状态逻辑；执行位置、鉴权和文件可达性分别检查 |
| 文案页、贴片设置、素材列表、时间轴 | 共用前端组件与状态；桌面多栏，手机分步/抽屉/底部面板，触摸操作单独验收 |
| 精确静帧、混合预览、本地导出 | 共用 RenderPlan 和结果合同；桌面媒体提供方与 Android Media3/MediaCodec 是不同执行实现 |
| Android 文件授权、Surface、后台任务与保存 | 需要独立原生适配和宿主接入，响应式 CSS 不能提供这些能力 |

“电脑浏览器打开手机工作台”和“DSH 在电脑本地运行”不同：前者的 Host/媒体计算仍可能在手机。桌面验收必须记录实际执行设备，不能仅按屏幕尺寸判断在哪里导出。

如果将所有剪辑和导出交给服务器，网页适配可以覆盖更大范围，但那会改变已提出的手机本地 1080P 导出要求。本轮不以服务器替代本地能力，也不承诺单靠 WebCodecs/WASM 已满足设备、内存、连续预览和后台矩阵。

## 开发顺序

1. **冻结共享工程合同。** 素材用句柄和内容摘要，不把电脑盘符路径写成跨端真相；明确源 PTS、裁切半开区间、工程修订、PNG 贴片及音轨。定义媒体提供方的 capability / job / result / cancel 合同。先以 Windows 为首个桌面目标，不推导其他桌面系统通过。
2. **桌面最小业务闭环。** 在真实 DSH 插件入口中完成“文案编辑与保存版本→示例/导入素材→创建工程→替换镜头/裁切→预览→1080P 导出→重开”。先用本地自制素材和可验证提供方，不用界面假结果代替成片。完整公司索引、TTS 和团队流程需接真实服务后才算通过。
3. **每个页面同步检查手机布局。** 用相同业务组件验证窄屏、触摸、软键盘、返回和遮挡；不要求此时完成手机性能优化。时间轴逐帧按钮、贴片操作和缓存等待从设计阶段保留，避免最后依赖鼠标悬停或塞满小屏幕。
4. **独立接入 Android 媒体适配器。** 复用已有验证模块，但生产 bridge、素材权限、原生画面与生命周期仍单独实现、评审和回归。保持 DSH 插件业务不侵入 `HarnessController` 等现有核心职责。
5. **收敛手机性能与支持矩阵。** 在目标 ARM64 真机验证同一黄金工程，比较帧边界、层顺序、贴片位置与声音；再优化代理/分镜缓存、直接预览、导出速度、内存、发热和后台行为。桌面通过不替代手机验收。

第 1 步的原生边界和第 3 步的手机交互不能全部推迟；第 5 步的性能优化可以后置。现有模拟器研究已经证明部分媒体路径可行，但[本轮复测](copy-edit-media-session-report.md)仍有播放间隔超标，不能描述成手机稳定性已解决。

## 当前交付边界

2026-11-08 已完成共享工程 v2、文案持久版本、PNG 贴片与桌面媒体提供方的最小闭环，真实 DSH 安装和 4/60 秒自制样本通过，详见[验收报告](copy-edit-desktop-mvp-report.md)。尚未制作完整编辑器，也未修改 DSHA 生产宿主。Android 原生接入与真机性能继续独立排期，不能由本次桌面或小屏浏览器结果推导通过。
