# 媒体丢帧与连续预览修复记录

日期：2026-11-07。范围：独立 `dsh.copyedit.spike` 与自制素材，复用获准的 `DSHA_API30` 模拟器。未修改 DSHA 宿主、插件运行协议、生产包或用户数据。最初失败见[前轮报告](copy-edit-plugin-spike-report.md)。

## 原因与证据

1. 未加背压时，Media3 1.11.1 的追踪显示解码器交出 120 帧，SurfaceTexture 收到 112 帧，GL 合成和编码均为 112 帧。两个素材开头分别丢 4 帧；不是编码器把完整的 120 帧编码成了 112 帧。
2. `ExternalTextureManager` 因缺帧等待其模拟器专用 20,000 ms 超时。这同时解释了接缝约 20.4 秒等待与导出约 45.7 秒。没有通过缩短超时假装修复。
3. 不经 Media3 的 Android `MediaCodec` / EGL / SurfaceTexture 对照：相同 `OMX.android.goldfish.h264.decoder`，设置 `KEY_ALLOW_FRAME_DROP=0`，60 帧按 5 帧批次投递，收到 12 个回调与 12 个不同 PTS；单帧准入收到 60/60，PTS 全部正确。消费者暂停 30 ms 的压力条件在两组相同，只有批次量不同。
4. 当前 API 30 模拟器的 Surface 批量投递行为可以在无 Media3、无贴片、无音轨的情况下复现；Media3 默认待接收量为 5，现有适配未处理这个组合。不能把问题泛化为 Media3 所有设备的缺陷，也不能声称 ARM64 手机同样会丢帧。

官方依据（固定版本，而非随最新文档推断）：[待接收帧数策略](https://github.com/androidx/media/blob/1.11.1/libraries/common/src/main/java/androidx/media3/common/util/Util.java)、[Surface 缺帧等待](https://github.com/androidx/media/blob/1.11.1/libraries/effect/src/main/java/androidx/media3/effect/ExternalTextureManager.java)、[解码器禁止丢帧设置](https://github.com/androidx/media/blob/1.11.1/libraries/transformer/src/main/java/androidx/media3/transformer/DefaultDecoderFactory.java)。

## 实现选择

- `SurfacePipeline`：仅在 API 30 / ranchu / 存在 Goldfish AVC 解码器的已复现环境启用单帧背压。Transformer 委托原解码器，改其准入量；直接合成预览使用 VideoGraph 的真实待接收计数控制准入。不伪造帧数、系统版本或设备身份，不修改 Media3 二进制，不增加任意 sleep 补丁。
- 背压修复后，4 秒导出恢复全部 120 帧。直接 CompositionPlayer 预览仍有约 339 ms 接缝延迟；降到 360×640 后仍约 279 ms。这个剩余延迟只定位到模拟器直接播放路径，没有足够证据在 Media3 切换调度和模拟器解码/图形准备成本之间单独定责。
- 当前正常预览使用本地 360×640 缓存：同一 RenderPlan、相同源 PTS 裁切、两路混音、多行透明 PNG，生成后由 ExoPlayer 连续播放。原素材仍用于 1080P 导出。界面显式展示准备状态；直接合成预览保留为诊断入口，未计入成功路径。
- 预览播放器启用 MediaCodec 异步队列；先暂停预滚首帧，再启动播放。暂停预滚和播放中间隔分别记录，门禁仍要求全部预期 PTS 完整、播放中最大间隔低于 150 ms。更早的同步队列试验有一次 119/120 回调，保留失败原件。
- 缓存只在同一 Activity、固定 4/60 秒自制计划内复用。新 Activity 重新生成，不复用磁盘残留作为已验证缓存。没有开发通用工程缓存、修改后局部失效、完整编辑器或后台任务系统。
- runner 只提取本次成功事件列出的 MP4，避免误读上轮残留文件。60 秒必须提供同一 APK 摘要、同一系统指纹、严格通过的 4 秒读回报告；单有仪器化 `OK` 不足以准入。

这些检查不等同于实际屏幕逐帧摄影或扬声器音画同步录测。当前编码器为模拟器的 `OMX.google.h264.encoder`，不能用耗时、内存或成功次数承诺普通手机的硬件编码性能。生产插件能力继续为 false，原生 `deviceVerified` 仍为 false。

## 生产边界与后续

当前全部代码留在 `experiments/copy-edit-media`。生产集成仍需独立 Android adapter、素材句柄、来源与页面代次、任务生命周期及 Surface 协作；不会通过增加聊天入口或修改现有桥来绕过这些边界。

后续先在获准的 ARM64 实体设备验证默认解码器路径与直接预览，再决定设备策略。缓存等待是否适合编辑体验、局部重建与取消、VFR/B 帧/60 fps 的完整成片、后台与存储故障均未因此完成。单主视频与多音轨成功也不能推导任意多视频叠加成功。
